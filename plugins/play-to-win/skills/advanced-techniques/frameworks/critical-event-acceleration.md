# Framework: Aceleracion de Critical Events

Sistema para identificar, establecer, documentar, y acelerar critical events que impulsan decisiones de compra. Un critical event es tan importante que impulsa una decision — si no ocurre, las consecuencias son negativas para el negocio del comprador. Basado en el concepto de Aceleracion de Eventos Criticos de la Metodología GrowthOS.

## Principios fundamentales

- **El CE pertenece al comprador, no al vendedor** — Un critical event real es una fecha de negocio del cliente (SKO, lanzamiento, regulacion, fin de contrato), nunca un deadline artificial del vendedor ("descuento valido hasta viernes")
- **Sin CE no hay urgencia** — Si el prospect no tiene un critical event, tu prioridad #1 es descubrir o crear uno. Sin urgencia real, los deals mueren de inercia
- **CE y Value son sal y pimienta** — Uno sin el otro no funciona. Un CE sin valor claro genera panico, no decision. Valor sin CE genera "interesante, pero no ahora"
- **Backward planning siempre** — Una vez establecido el CE, trabaja hacia atras para definir cada hito. Si los hitos no cuadran, el CE no es realista y necesitas renegociar la fecha
- **El tipo de comprador determina tu estrategia** — No todos los compradores se tratan igual. Diagnostica primero, actua despues

## Progresion de Prioridad

El comprador pasa por 4 estados de prioridad respecto a tu solucion. Cada estado tiene una dinamica diferente:

```
         PRIORIDAD BAJA                                    PRIORIDAD ALTA
              │                                                  │
              v                                                  v

Tiempo ─────────────────────────────────────────────────────────────>

  Estado 1          Estado 2           Estado 3          Estado 4
  NICE-TO-HAVE      NEED-TO-HAVE       GOES DARK         MUST-HAVE
  ┌──────────┐      ┌──────────┐      ┌──────────┐      ┌──────────┐
  │ "Seria   │      │ "Lo      │      │ Sin      │      │ "Lo      │
  │  bueno   │ ──>  │  necesi- │ ──>  │ respuesta│ ──>  │  necesito│
  │  tenerlo"│      │  tamos"  │      │ Oscuro   │      │  YA"     │
  └──────────┘      └──────────┘      └──────────┘      └──────────┘

  Trigger:           Trigger:          Trigger:          Trigger:
  No ha vivido       Reconoce la       Subestimo el      Problema volvio
  el problema        severidad         deadline          a ocurrir

  Accion:            Accion:           Accion:           Accion:
  EDUCAR             ASISTIR           DISTANCIARTE      ASISTIR
                                       (posible NO BID)   RAPIDAMENTE
```

**Insight clave**: La progresion no es lineal ni predecible. Un comprador puede saltar del estado 1 al 4 si ocurre un evento externo (cambio de CEO, regulacion, perdida de cliente clave). Tu trabajo es detectar en que estado esta y actuar en consecuencia.

## Los 4 Tipos de Comprador

| # | Situacion | Comportamiento tipico | Estrategia del vendedor | Riesgo si actuas mal |
|---|-----------|----------------------|------------------------|---------------------|
| **1** | No ha experimentado el problema | Curiosidad superficial, "estamos explorando opciones", calls cortas, no involucra stakeholders | **Educar** con referencias de terceros. Compartir historias de empresas similares que no actuaron a tiempo. Datos de industria. | Si presionas, te perciben como agresivo y cierran la puerta |
| **2** | Reconoce la severidad, necesita solucion | Busca activamente, compara opciones, involucra equipo, pide demos, tiene preguntas especificas | **Asistir** en el proceso de trade-offs. Guiar la evaluacion con tu expertise. Facilitar, no vender. | Si no guias, el competidor define los criterios y pierdes |
| **3** | Subestimo el problema, paso el deadline, se fue oscuro | No responde emails, cancela calls, "estamos revisando internamente", semanas sin contacto | **Distanciarte**. Enviar un email de "puerta abierta" y considerar **NO BID**. No perseguir desesperadamente — destruye tu posicion. | Si persigues, pareces desesperado y reduces tu poder de negociacion a cero |
| **4** | Problema volvio a ocurrir — es HOT lead | Urgencia maxima, quiere resolver ya, responde rapido, pregunta por implementacion inmediata, escala internamente | **Asistir rapidamente**. No bloquear el proceso con burocracia interna. Facilitarle todo. Este es tu mejor escenario. | Si eres lento o burocratico, pierdes la ventana de urgencia |

### Script para diagnosticar el tipo de comprador

Usa estas preguntas en los primeros 5 minutos:

1. **"Han experimentado este problema antes?"** → Si no: Tipo 1. Si si: continua.
2. **"Cuando ocurrio por ultima vez?"** → Reciente: Tipo 2 o 4. Hace tiempo: Tipo 1 o 3.
3. **"Que paso cuando ocurrio?"** → Si hubo consecuencias serias: Tipo 4. Si fue "manejable": Tipo 2.
4. **"Han intentado resolverlo antes?"** → Si lo intentaron y fallo: Tipo 3 o 4. Si nunca: Tipo 1 o 2.
5. **"Hay una fecha especifica en la que esto necesita estar resuelto?"** → Si hay fecha: Tipo 2 o 4. Si no: Tipo 1 o 3.

## Establecer el Critical Event Date

### La tecnica de 3 preguntas

Esta secuencia progresiva lleva al comprador a articular su propio CE con consecuencias:

### Pregunta 1: "Cuando necesitas esto en funcionamiento?"

**Objetivo**: Establecer una fecha concreta.

**Variaciones**:
- "Para cuando necesitan tener esto resuelto?"
- "Hay una fecha especifica en la que necesitan estar operando con la nueva solucion?"
- "Cuando es el deadline real para que esto este en produccion?"

**Si no tienen fecha**: "Si no hubiera limitaciones, cuando les gustaria tenerlo listo?" Esto crea un ancla temporal que puedes trabajar.

### Pregunta 2: "Y que pasa si no llegas a esa fecha?"

**Objetivo**: Establecer consecuencias concretas.

**Variaciones**:
- "Que le pasa al negocio si esa fecha se mueve 3 meses?"
- "Quien se ve afectado si no se cumple ese timeline?"
- "Cual es el costo de no tener esto para esa fecha?"

**Clave**: Las consecuencias deben ser del comprador, no tuyas. "Perdemos el quarter" es una consecuencia real. "Nos gustaria tenerlo antes" no lo es.

### Pregunta 3: El cierre del CE

> "Si necesitas esto funcionando para **{fecha}** para obtener **{impacto}** o enfrentar **{consecuencia}**... como podemos ayudarte a llegar ahi?"

**Estructura**: Esta pregunta resume lo que el comprador dijo (no lo que tu quieres que diga) y te posiciona como facilitador, no como vendedor.

**Ejemplo**:
> "Si necesitas el nuevo CRM funcionando para el **15 de julio** para tener visibilidad completa antes del **SKO de agosto** o enfrentar que **el equipo siga operando a ciegas otro quarter**... como podemos ayudarte a llegar ahi?"

## Backward Planning (Pelar la Cebolla)

Una vez establecido el CE, construye el timeline hacia atras. Cada hito tiene una fecha que depende del siguiente:

```
┌─────────────────────────────────────────────────────────────────┐
│ BACKWARD PLANNING: De Go-Live hacia atras                        │
│                                                                  │
│  CE: Go-Live ─── Jul 15                                         │
│      ↑                                                           │
│  Integracion completa ─── Jul 2 (2 semanas)                     │
│      ↑                                                           │
│  Desarrollo/Config ─── Jun 1 (4 semanas)                        │
│      ↑                                                           │
│  PO firmado ─── May 29 (kick-off)                               │
│      ↑                                                           │
│  Legal/Procurement ─── May 15 (2 semanas)                       │
│      ↑                                                           │
│  Decision final ─── May 8 (1 semana)                            │
│      ↑                                                           │
│  Propuesta presentada ─── May 1                                 │
│      ↑                                                           │
│  HOY ─── Abr 20                                                 │
│                                                                  │
│  Margen de maniobra: 11 dias (Abr 20 → May 1)                  │
│  Si el margen es negativo → CE no es realista → renegociar      │
└─────────────────────────────────────────────────────────────────┘
```

### Reglas del backward planning

1. **Siempre incluir legal/procurement** — Es donde mas deals se retrasan. Preguntar: "Cuanto tarda procurement tipicamente?"
2. **Agregar buffer de 10-15%** — Los timelines siempre se expanden, nunca se contraen
3. **Si el margen es negativo, decirlo** — "Basado en este timeline, la unica forma de llegar a julio es tomar la decision esta semana. Es eso posible?"
4. **Involucrar al champion en el backward plan** — El champion necesita defender el timeline internamente
5. **Documentar cada hito con responsable** — Sin responsable, el hito no existe

## Seller-Centric vs Customer-Centric Timeline

```
SELLER-CENTRIC (como piensan muchos vendedores):

  "Necesito el PO para fin de mes"
  ─────────────────────────────────>
  Prospecting → Demo → Propuesta → Negociacion → PO → ✓ Comision

  Problema: Todo gira alrededor de TU deadline, no del cliente.


CUSTOMER-CENTRIC (como deberias pensar):

  "El cliente necesita estar en produccion para julio"
  <─────────────────────────────────
  Go-Live Jul 15 ← Integracion ← Config ← PO ← Legal ← Decision ← Hoy

  Ventaja: El timeline se justifica solo. El PO es una consecuencia
  natural del backward plan, no un pedido del vendedor.
```

**Regla de oro**: Empieza siempre desde la fecha de go-live del cliente, nunca desde tu fecha de PO. El PO aparece naturalmente como un hito del backward plan.

## Email de Confirmacion de Critical Event

Despues de establecer el CE en una llamada, enviar un email standalone dentro de las 24 horas. No lo entierres en un follow-up general — merece su propio email.

### Formato del email

**Subject**: Confirmacion: {nombre de la solucion} en funcionamiento para {fecha CE}

**Body**:

```
Hola {nombre},

Gracias por la conversacion de hoy. Quiero confirmar lo que acordamos:

CRITICAL EVENT:
- Fecha objetivo: {fecha CE}
- Necesidad: {que necesitan lograr para esa fecha}
- Impacto si se cumple: {impacto positivo}
- Consecuencia si no se cumple: {consecuencia negativa}

TIMELINE DE TRABAJO (hacia atras desde {fecha CE}):
- {Hito 1}: {fecha} — Responsable: {nombre}
- {Hito 2}: {fecha} — Responsable: {nombre}
- {Hito 3}: {fecha} — Responsable: {nombre}
- {Hito 4}: {fecha} — Responsable: {nombre}

SIGUIENTE PASO:
- {accion concreta} para {fecha}, liderado por {responsable}

Por favor confirma que este timeline refleja correctamente lo que
discutimos. Si algo cambio, necesitamos ajustar ahora para no
comprometer la fecha de {fecha CE}.

Saludos,
{tu nombre}
```

**Claves del email**:
- Usa las palabras exactas del cliente, no las tuyas
- Incluye consecuencias — esto crea accountability
- Pide confirmacion explicita — un email sin respuesta no vale
- El siguiente paso debe ser concreto (que, quien, cuando)

## Relacion Critical Event <-> Value

CE y Value son sal y pimienta — uno sin el otro no funciona:

```
┌─────────────────────────────────────────────────┐
│                                                  │
│  Value alto + CE fuerte = DEAL SE CIERRA         │
│  "Genera $2M/ano y lo necesitan para julio"      │
│                                                  │
│  Value alto + CE debil = DEAL SE RETRASA         │
│  "Genera $2M/ano pero... no hay urgencia"        │
│                                                  │
│  Value bajo + CE fuerte = DEAL EN RIESGO         │
│  "Lo necesitan para julio pero... $50K/ano?"     │
│                                                  │
│  Value bajo + CE debil = DEAL MUERTO             │
│  "Nice-to-have sin fecha... siguiente."          │
│                                                  │
└─────────────────────────────────────────────────┘
```

**Diagnostico rapido**: Si tu deal tiene value alto pero se retrasa, el problema es el CE. Si tiene CE pero el prospect no quiere pagar, el problema es el value. Soluciona el deficit, no todo a la vez.

### Test de los 90 dias

Pregunta clave para validar que el CE es real:

> **"Hay alguna razon por la cual NO podrian implementar esto en los proximos 90 dias?"**

**Interpretacion de respuestas**:

| Respuesta | Significado | Accion |
|-----------|------------|--------|
| "No, ninguna razon" | CE implicito de 90 dias. Tienes urgencia. | Construir backward plan de 90 dias |
| "Si, presupuesto" | Bloqueador financiero. No es timing. | Resolver presupuesto antes de avanzar |
| "Si, decision interna" | Falta alineacion de stakeholders | Activar relationship mapping, identificar bloqueadores |
| "Si, otro proyecto tiene prioridad" | Competencia interna por recursos | Cuantificar costo de esperar vs. actuar ahora |
| "Si, no estamos listos" | No han reconocido la severidad. Tipo 1. | Volver a educacion con referencias |

## Errores comunes

| Error | Consecuencia | Correccion |
|-------|-------------|------------|
| Crear urgencia artificial ("descuento valido hasta viernes") | El prospect desconfia y se distancia | Usar urgencia real del negocio del comprador |
| No preguntar por consecuencias del CE | El CE no tiene peso — es solo una fecha | Siempre preguntar "que pasa si no llegas?" |
| Ignorar el backward planning | Descubres tarde que el timeline no cuadra | Construir backward plan inmediatamente despues de establecer el CE |
| Tratar a un comprador Tipo 3 como Tipo 2 | Persigues a alguien que no va a comprar | Diagnosticar el tipo antes de invertir esfuerzo |
| Usar tu timeline (PO date) en vez del cliente | Te perciben como vendedor, no como partner | Siempre empezar desde el go-live del cliente |
| No enviar email de confirmacion | El CE queda "en el aire", nadie se compromete | Email standalone dentro de 24 horas, pidiendo confirmacion |
